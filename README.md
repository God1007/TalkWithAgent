# TalkWithAgent

任务执行留在 Codex，讨论在网页中。**你和 agent 都可以主动发起话题**，并在各自话题里追问、提建议、补充信息，再把确定的结论交给执行端。

## 启动

需要 Python 3.10+、已登录的 Codex CLI（支持 `exec resume --output-schema`）。没有前端构建步骤或第三方 Python 依赖。

```bash
python3 server.py --main-thread <当前-Codex-任务-ID>
```

打开 http://127.0.0.1:8765 。可用 `--port` 换端口，`--data-dir` 指定本地记录目录（默认 `.runtime/`）。这是单用户本地服务。

## 双向讨论

- 你可以随时点击“发起话题”。agent 思考期间也可以开启别的话题或继续补充，输入会持久化排队。
- Codex 发布新进展后，讨论 agent 自动思考是否值得发起话题，无需用户先发消息；没有新问题时保持安静。
- 双方的话题放在同一列表，用发起者、类型、未读标记区分。每个话题保留独立消息；agent 话题附带触发它的任务进展。
- 问题和方案的候选回答先填入回复框，你可以修改并继续讨论。“采纳 / 不采纳”会提交明确反馈，“稍后再聊”不提交答案。
- “把结论交给 Codex”会让你确认要提交的文字。结论先存入回传队列，执行 agent 确认读取后才显示“Codex 已读取”。
- 历史、队列和讨论 thread id 保存到 SQLite；输入草稿按会话、话题保存在浏览器。刷新可恢复，旧版记录归入“先前的讨论”。

页面按话题组织，宽屏同时显示列表和讨论，窄屏可进入话题再返回列表。顶部“任务动态”可以查看同步进展、会话关联和切换记录。

## Codex 与网页互通

网页 URL 的 `session=` 是讨论记录 id，并非 Codex thread id。执行 agent 用它发布检查点、读取用户明确提交的结论：

```bash
python3 bridge.py --session <讨论记录-ID> publish '已完成接口分析，正在实现页面'
python3 bridge.py --session <讨论记录-ID> pending
# 理解消息后确认读取；ack 不代表已经执行。
python3 bridge.py --session <讨论记录-ID> ack <消息-ID>
python3 bridge.py --session <讨论记录-ID> publish '本轮任务完成' --status completed
```

进展更新会自动触发模型调用，相同进展不重复触发；连续更新合并后再思考，过期结果不会生成新话题。每个讨论会话串行调用同一个持久化 Codex thread。agent 使用稳定话题标识去重，最多同时提出四个尚未处理的话题。

页面每 1.2 秒读取本地状态，后台没有新输入时不调用模型。调用失败会显示重试入口，历史和排队消息仍然保留；重复请求使用 request id 去重。

## 当前边界

这是可运行的 demo，尚未封装成可安装插件。主会话采用**显式检查点同步**，不自动订阅完整桌面会话，不在主 agent 结束后自动唤醒它。`--main-thread` 只是关联标识，不授予主会话控制能力。自动思考发生在服务收到新进展之后。

讨论 agent 是服务创建的独立 Codex thread，还不是桌面任务树中原生派生的 sub-agent。它只能看到已同步的进展和讨论内容。调用使用本机 Codex 登录，会消耗对应账户额度。

只有执行端上报 `waiting` 时，讨论 agent 才能提出决策话题；它不能自行暂停执行端。真实阻塞与恢复、原生子任务关联、自动实时回传和插件打包仍需后续接入。

讨论调用使用只读 sandbox。服务绑定 `127.0.0.1`，验证 Host/Origin 和 JSON 自定义请求头，没有多用户认证，不应暴露到公网。不要上传包含任务内容的 `.runtime/`。

## 验证

```bash
python3 check.py
node --check app.js
```

检查覆盖双方发起、进展自动触发、重复及过期话题过滤、显式回传与读取确认、失败重试、重启恢复、旧记录迁移和会话隔离。浏览器实际聊天需要可用的 Codex 登录和网络。
